## Inspiration

People have started asking AI assistants to shop for them. When we asked for "a speckled mug from a small
studio", the assistant found real independent makers, but only as links out of the chat. It could recommend a
small shop. It couldn't buy from it.

Big retailers are getting agent integrations, product feeds and checkout APIs. A one-person pottery studio has
an Instagram caption and a "DM to order" button. If shopping moves into assistants, the smallest sellers are the
first to disappear from it. We wanted the opposite: a maker should be buyable by an assistant as easily as they
can post a photo.

## What it does

Shelf has two sides.

**Sellers** paste their shop link or a messy product list ("speckled mug 28 / celadon cup 34 — ~8oz /
platter DM for price"). Claude extracts the shop and its products, then writes what agents need: clean
descriptions, tags for use case, style, material and gifting, and structured attributes like dimensions,
capacity and care. Channel3 returns market price comps for every product and suggests a price when the seller
didn't list one. The seller reviews it all in an AG Grid editor where every AI-written cell is highlighted, adds
their PayPal email, and presses Publish.

**Shoppers** connect Shelf to their assistant once. It's a remote MCP server, added to Claude Desktop as a
custom connector. From then on:
- `search_products` returns Shelf shops first, buyable in chat, with Channel3 results from the wider market
  below, clearly labeled as link-out only.
- `create_checkout` creates a PayPal order with **the seller as the payee** and returns a PayPal approval link.
- The buyer approves on PayPal. Shelf captures the payment and `check_order` confirms it's paid.

The assistant never pays on its own: the buyer approves every payment on PayPal, and the money goes straight to
the seller's PayPal account. Shelf never holds funds.

**After publishing**, the seller's dashboard shows a live AG Grid of orders that flashes the moment PayPal confirms
a payment, showing which assistant made the sale and what the shopper asked for. A second grid shows what
assistants searched for across the network, and Claude turns unmet searches into suggestions ("agents asked for
a speckled bowl five times this week").

Every shop also gets a public page with schema.org Product/Offer JSON-LD, and `/llms.txt` lists the MCP endpoint
and all published shops, so shops can be discovered on the open web too.

## How we built it

- **Next.js 15** (App Router, TypeScript, Tailwind v4) as one Node web service on **Render**, with **Render
  Postgres** for shops, products, orders, the agent search log and webhook de-duplication.
- **PayPal** through `@paypal/paypal-server-sdk` (generated by **APIMatic**): Orders v2 create, get and capture,
  with `payee.email_address` set to the seller, an item breakdown and an experience context (brand
  "Shelf · {shop}", `PAY_NOW`, return and cancel URLs). The return URL captures right away; webhooks are
  signature-verified with `verify-webhook-signature`, de-duplicated by event id, and also drive order status
  (approved, paid, refunded or failed), so a payment is recorded even if the buyer closes the tab.
- **MCP**: the official TypeScript SDK with stateless streamable HTTP (a new server and transport per request,
  JSON responses). Four tools with zod schemas return both readable text and `structuredContent`. Orders record
  which assistant placed them, from MCP `clientInfo` or the User-Agent.
- **Claude**: Sonnet 5.5 for catalog extraction and enrichment, with each AI-written field tracked in
  `ai_fields`. Haiku 5.5 ranks search candidates after a lexical prefilter, writes a one-line "why" per hit and
  drops irrelevant products; it also writes the demand insights. Search falls back to lexical ranking if the
  model times out.
- **Channel3**: wider-market results in agent search, and low/median/high price comps per imported product.
- **AG Grid Community v36**: the catalog editor (AI-cell highlighting, market range column), the live orders grid
  (row flashing on payment), and the agent demand grid.
- A fictional ceramic studio, **Hanul Clay**, built as a plain static site with no structured data, so the demo
  imports a messy real-looking page rather than a clean feed.

## Challenges we ran into

- **Making checkout safe for agents.** An assistant should never be able to spend money on its own. The design
  keeps the buyer on PayPal's approval page for every order, and the MCP instructions tell the model never to
  claim payment until `check_order` says it's paid.
- **Routing money to the seller, not the platform.** Payee routing on Orders v2 sends funds straight to each
  shop's PayPal account without Shelf touching them.
- **Payment state from two directions.** The return URL and the webhook can both report the same payment, in
  either order. Capture is idempotent, webhook events are de-duplicated, and order status never moves backwards
  from paid or refunded.
- **Refunds when the seller is the payee.** We built platform refunds with Payments v2, then tested one on a
  payee-routed sandbox capture: PayPal answered `PERMISSION_DENIED`. The capture belongs to the seller, so
  refunding it needs the seller's partner permission. Sellers refund from their own PayPal account for now, and
  partner onboarding is the path to refunds from the Shelf dashboard.
- **Search that agents can trust.** Lexical search returned candles for "mug". A small model reranking the
  candidates fixed relevance, with a strict timeout and lexical fallback so search never hangs a conversation.
- **Messy input.** Real small-shop pages and captions have prices in prose, missing sizes and "DM for price".
  Tracking which fields the AI wrote let us show sellers exactly what to check.

## Accomplishments that we're proud of

- A brand-new shop goes from a pasted link to a PayPal checkout inside Claude in about two minutes.
- Payment goes straight to the seller, and the buyer stays in control of every payment.
- The seller sees agent demand they couldn't see before: which assistant sold their mug, and what agents asked
  for that they don't make yet.
- No install for sellers, and a one-time connector for shoppers.

## What we learned

- MCP is a good shape for commerce: a few narrow tools with clear instructions make the model reliable about
  showing approval links and checking status instead of assuming.
- PayPal's approval step is a feature for agentic commerce, not friction. It's the moment the human says yes.
- Agents need different product data than people do. Dimensions, care and capacity decide whether an assistant
  can confidently recommend something.

## What's next for Shelf

- **Discovery without a connector**: publish Shelf shops as product feeds to catalogs like Channel3 and to open
  agent directories, building on the JSON-LD and `/llms.txt` we already serve.
- **PayPal partner onboarding** so sellers connect their PayPal account in one click, Shelf can take a small
  platform fee per sale, and, with the seller's refund permission, refunds can be issued from the dashboard.
- Shipping rates, taxes and order tracking (PayPal order tracking API), plus inventory sync.
- Photo import: snap a shelf of pots and get a catalog.

## Tools used

| Tool | Where in Shelf |
|---|---|
| **PayPal Orders API v2** | Create orders with seller payee routing, item breakdown and experience context; get order status; capture after buyer approval (`lib/checkout.ts`, `lib/paypal.ts`, `app/api/paypal/return`) |
| **PayPal Webhooks** | Signature verification, event de-duplication, status updates for approved, completed, refunded, reversed and denied events (`app/api/paypal/webhook`, `scripts/register-webhook.mts`) |
| **PayPal Sandbox** | All payments in the demo: business accounts for sellers, personal account for the buyer |
| **APIMatic** | `@paypal/paypal-server-sdk`, APIMatic-generated, used for every Orders v2 call (`OrdersController`: create, get, capture) |
| **AG Grid** (Community) | Catalog editor, live orders grid with row flashing, agent demand grid (see them at `/dash/demo`) |
| **Channel3** (`@channel3/sdk`) | Market results in agent search (link-out), price comps and suggested prices in the catalog editor |
| **Render** | Web service (app, MCP server, PayPal endpoints), Render Postgres, static site for the demo shop, `render.yaml` Blueprint |
| **Anthropic Claude API** | Sonnet 5.5: catalog extraction and enrichment. Haiku 5.5: search ranking and demand insights |
| **Model Context Protocol TypeScript SDK** | The Shelf MCP server at `/api/mcp` (streamable HTTP) |
| **Claude Code** | Development assistant used to build the project |

## Testing instructions for judges

1. Claude Desktop → Settings → Connectors → Add custom connector → URL `<HOSTED_URL>/api/mcp`.
2. In a browser tab, open `<HOSTED_URL>/dash/demo`: Hanul Clay's seller dashboard, read-only (the seller's
   PayPal email and buyer details are hidden). Leave it open.
3. Ask Claude: "Find me a speckled mug from a small studio under $40, I'd like to buy it."
4. Ask Claude to buy it, open the PayPal link, and log in with the sandbox buyer:
   `<SANDBOX_BUYER_EMAIL>` / `<SANDBOX_BUYER_PASSWORD>`.
5. Ask Claude "did it go through?". `check_order` reports paid.
6. Back on the dashboard tab, your order row flashes as paid, with "Claude" as the assistant and what you asked.
   Scroll down for the agent demand grid and press "Analyze demand" for insights.
7. To try the seller side yourself, open `<HOSTED_URL>/sell`, paste `<DEMO_SHOP_URL>` (or any small shop page),
   and publish with a sandbox business email. Your shop gets its own private dashboard link.

The free Render instance sleeps when idle, so the first request may take up to a minute. All shops other than
those you create are demo data, and Hanul Clay is a fictional studio.
